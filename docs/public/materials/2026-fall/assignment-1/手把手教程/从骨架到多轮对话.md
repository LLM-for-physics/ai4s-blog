# 从骨架到多轮对话

从一个能打开网页的小程序出发，边运行、边理解、边修改同一个 `app.py`，逐步完成自己的作业。

本教程采用 **Python + Flask + Requests**：Flask 接收浏览器请求，Requests 调用模型，列表和字典保存消息。网页写在 Python 字符串中，无需另写 JavaScript。

先按[运行指南](运行指南.md)启动骨架。正文提供改动思路和局部示例，包内没有最终整合程序。代码块会标明用途；根据说明修改相应位置，不要把所有片段依次粘到文件末尾。

## 1. 读懂起始骨架

在网页输入“你好”，会看到“这是演示回复，我收到了：你好”。目前没有模型参与，我们先看清网页与 Python 如何配合。

### 一次发送经过了哪里

```text
浏览器提交表单
    ↓
index() 读取问题
    ↓
get_reply() 生成演示回复
    ↓
make_page() 将内容拼成网页
    ↓
浏览器显示结果
```

文件中只有三个自己定义的函数：

| 函数 | 作用 |
| --- | --- |
| `get_reply(question)` | 接收问题字符串，返回回复字符串 |
| `make_page(question, answer, error_text)` | 将问题、回复和提示拼成 HTML |
| `index()` | 接收请求，组织前两个函数的调用 |

接入模型主要改 `get_reply()`，修改显示主要改 `make_page()`，控制调用和保存则在 `index()` 中完成。

顶部的 `Flask(__name__)` 建立应用。末尾的 `if __name__ == "__main__":` 表示直接运行文件时才执行启动语句；`app.run()` 启动服务，等待浏览器请求。无需自己写 `while` 循环等待输入。

### 表单与 Python 怎样对应

在 `make_page()` 中找到这段 HTML：

```html
<form action="/" method="post">
```

`form` 是表单，`action="/"` 指定提交到首页，`method="post"` 指定提交方式。输入框的 `name="question"` 对应 `index()` 中的这行：

```python
question = request.form.get("question", "").strip()
```

`get()` 按字段名取值，缺失时返回空字符串；`strip()` 去掉首尾空白。打开网页通常产生 GET，按发送产生 POST，因此只在 POST 分支中读取问题并回复。

文件末尾的 `app.add_url_rule()` 将 `/` 与 `index` 关联，并允许 GET、POST。`view_func=index` 传入函数本身；有请求时 Flask 才调用它，所以这里不写 `index()`。

### Python 字符串怎样变成网页

`make_page()` 用 `page = page + ...` 拼接字符串，再 `return page`。浏览器将其中的 HTML 标记显示为页面：`h1` 是标题，`p` 是段落，`textarea` 是输入框，`button` 是按钮。`pre` 保留换行，`white-space: pre-wrap` 允许长行折行。

用户输入和模型回复显示前要经过 `html.escape()`。这样 `<b>你好</b>` 会显示为原文，而不会被解释为网页标签。固定的 HTML 标记不用转换，动态插入的文字需要转换。

> **试一试**：修改标题和演示回复，保存、停止并重启程序。再发送空白和 `<b>你好</b>`，检查提示与原文显示。起始骨架只显示最近一次结果，输入框保留刚才的文字，还没有历史功能。

## 2. 接入真实模型

现在 `get_reply(question)` 接收一个字符串、返回一个字符串。先保持这个接口不变，只替换函数内部生成回答的方式。

### 读取三项配置

按[运行指南](运行指南.md)设置完整请求地址、模型名称和 API Key。本教程使用 Chat Completions 格式的接口。

文件顶部增加 `import os` 和 `import requests`，然后在函数外读取配置：

```python
api_url = os.environ.get("LLM_API_URL", "")
api_key = os.environ.get("LLM_API_KEY", "")
model_name = os.environ.get("LLM_MODEL", "")
```

这些值在启动时读取，修改配置后要重启。在 **`get_reply()` 开头**检查三项是否为空；缺少配置时，可用 `raise ValueError("请先配置 API 地址、模型和 Key。")` 表示本次调用失败。后面会在调用处处理它。

### 准备消息和请求

接口接收的是带身份的消息列表。在 `get_reply(question)` 内，先把当前问题表示为：

```python
messages = [{"role": "user", "content": question}]
```

`[]` 是列表，`{}` 是字典。`role` 表示说话者，`user` 代表用户，`content` 是正文。

接着准备两个字典：`headers` 保存认证信息，`data` 保存请求内容。

| 字典 | 字段 | 对应的值 |
| --- | --- | --- |
| `headers` | `Authorization` | `"Bearer "` 加上 `api_key`，保留中间空格 |
| `data` | `model` | `model_name` |
| `data` | `messages` | 刚准备的消息列表 |
| `data` | `stream` | Python 的 `False`，等待完整回答 |

变量准备好后，在 `get_reply()` 中使用下面的局部写法：

```python
response = requests.post(
    api_url, headers=headers, json=data, timeout=60,
    allow_redirects=False
)
response.raise_for_status()
result = response.json()
```

`json=data` 将字典按 JSON 格式发送；`timeout` 设置网络等待超时；`allow_redirects=False` 不跟随地址跳转。`raise_for_status()` 检查 HTTP 错误，`response.json()` 把正文解析为 Python 数据。

典型的**返回数据**如下，不要把它写死进程序：

```json
{
  "choices": [
    {"message": {"role": "assistant", "content": "你好！"}}
  ]
}
```

用 `result["choices"][0]["message"]["content"]` 依次取出候选列表、第一项、消息和正文。把正文记为 `answer`，检查它是非空字符串，再用 `return` 返回。`isinstance(answer, str)` 可检查类型；确认是字符串后，再用 `answer.strip()` 检查是否只有空白。格式不对时抛出 `ValueError`。

原来的演示 `return` 要移除，否则函数会提前返回。完成后，`get_reply()` 应按顺序完成：检查配置、准备请求、发送请求、提取并返回回答。

### 调用失败时显示提示

在 `index()` 的非空输入分支中，把原来的单行调用改成下面的形式，保留它所在的缩进：

```python
try:
    answer = get_reply(question)
except (
    requests.RequestException, ValueError,
    KeyError, IndexError, TypeError
):
    error_text = "未能取得回答，请检查配置、网络和返回数据。"
```

成功时得到 `answer`；出现指定类型的错误时执行 `except`，页面通过 `error_text` 显示提示。这些类型覆盖常见网络、配置、解析和返回结构错误；其他程序错误仍需查看终端中的报错行号。

> **试一试**：重启后发送简单问题，确认收到真实模型回答，并把网页的演示说明改成实际状态。若失败，可在请求后临时打印 `response.status_code` 辅助排查，不要打印 Key 或认证头。

此时只有单轮问答。成功后直接显示 POST 结果，刷新可能重复发送；先避免刷新结果页，第 4 节会处理。

## 3. 为请求加入上下文

先说“样品甲的质量是 3 千克”，再问“它的两份总质量是多少”。现在第二次请求只有后一句，接口不会自动保存第一次问答。上下文需要由程序保存，并随下一次请求一起发送。

### 建立历史列表

在文件顶部、`app = Flask(__name__)` 后加入 `history = []`，保存已完成的问答。不要放进 `index()`，否则每次请求都会重新建立空列表。

一轮完成后的**数据形状**类似：

```python
[
    {"role": "user", "content": "样品甲的质量是 3 千克。"},
    {"role": "assistant", "content": "好的，我记住了。"}
]
```

程序应从空历史开始，存入实际问题和回答；不要把示例文字当成真实历史。模型回答的角色是 `assistant`。

### 同步修改函数与调用处

消息列表现在应由了解历史的 `index()` 准备，需要一起调整三处：

| 位置 | 修改方式 |
| --- | --- |
| 函数定义 | 将 `get_reply(question)` 改为 `get_reply(messages)` |
| 函数内部 | 删除“只用当前问题重新建立 messages”的语句，请求体使用传入列表 |
| `index()` 调用处 | 先准备完整消息列表，再传给 `get_reply()` |

返回值仍是回答字符串，配置、网络请求和结果解析可以沿用。

### 为本次请求另建列表

在 `index()` 的非空输入分支中，将当前问题表示为用户消息；另建一个请求列表，依次放入历史消息，再放入当前问题。

不要直接写 `messages = history`：这会让两个变量指向同一个列表，追加问题就提前改动了历史。先看这个独立例子：

```python
saved = ["甲", "乙"]
working = []
for item in saved:
    working.append(item)
working.append("丙")
print(saved)    # ['甲', '乙']
print(working)  # ['甲', '乙', '丙']
```

将这个思路用于消息组织。这里复制外层列表，旧消息字典仍被引用；我们只追加新消息，不修改旧字典，因此可以这样做。

### 成功后再保存完整问答

请求列表是准备发送的内容，`history` 是已经完成的问答。只有 `get_reply()` 正常返回，才把本次用户消息及相应的 `assistant` 消息按顺序追加进历史。

在已有 `try/except` 后增加同一级缩进的 `else:`，把两条消息的保存放在这里。`else` 仅在 `try` 没有报错时执行。不要只存用户消息，也不要把失败提示存成模型回答。

> **试一试**：连续问两个依赖前文的问题，在调用前临时 `print(messages)`。不额外添加系统消息时，三次请求应分别包含 1、3、5 条消息。页面此时仍只显示最近一轮；先确认模型实际收到历史，再完善显示。

## 4. 显示整段历史

让页面从 `history` 读取内容，GET 就能重新显示整段会话，无需依赖刚才 POST 中的单条问题与回答。

### 改变页面函数的输入

将函数参数改为 `make_page(history, error_text, input_text)`，分别表示历史、错误提示和输入框中保留的文字。

同步把 `index()` 最后的调用改为 `make_page(history, error_text, question)`；若自己增加过其他返回分支，也要一起改。调用处的 `question` 传入后叫 `input_text`，名称可以不同，但位置和含义要对应。

在 `make_page()` 内完成两处替换：

- 删除原来的 `if answer != "":` 判断及其显示最近问答的整个代码块，在原位置改为遍历 `history`，不再使用单独的 `answer` 和 `question`。
- 输入框中原来的 `question` 改用 `input_text`。

标题、错误提示、表单及最后的 `return page` 可以保留。

### 用循环生成消息区域

在标题和错误提示后、表单前，用 `for message in history:` 逐条取出消息。读取 `message["role"]` 决定显示“我”还是“AI”，读取 `message["content"]` 作为正文。

沿用骨架中的拼接方法：先追加身份段落，再追加正文的 `pre` 段落。正文仍需 `html.escape()`。每条消息的显示代码放在循环内；页面开头、表单和 `return page` 放在循环外，否则可能重复输入框或只显示第一条消息。

空历史会让循环执行零次，页面仍应有输入框。保存并重启，确认两轮问答都能显示。

### 成功后跳转，避免刷新重复发送

在 Flask 导入中增加 `redirect`。在 `index()` 成功保存问答的分支末尾，使用 `return redirect("/", code=303)`。浏览器随后 GET 首页，只读取历史，不再次调用模型。

函数末尾的 `return make_page(...)` 仍要保留，用于首次 GET、空输入和调用失败。失败时保留 `question` 供修改；成功跳转后的 GET 会把它初始化为空，输入框自然清空。不要同时清空 `history`。

> **试一试**：发送两轮后刷新页面，历史应保留，且不产生新模型请求。等待回复时只点一次发送；303 跳转解决的是成功后刷新，没有防止连续点击的功能。

## 5. 新建并切换会话

新建时应保留旧历史，再创建一段空历史。直接清空原来的 `history` 会丢失旧记录。

### 用外层列表保存多段会话

将文件顶部的 `history = []` 替换为 `conversations = [[]]`。外层列表保存各段会话，内层列表保存该会话的消息：

```text
conversations
  [0] 第一段对话的消息列表
  [1] 第二段对话的消息列表
  [2] 第三段对话的消息列表
```

先在 `index()` 中用 `history = conversations[0]` 选择第一段，后面的请求、保存和显示继续使用 `history`。运行确认原有功能正常，再加入编号选择。

这里故意引用原列表，追加消息才能存回所选会话；第 3 节准备请求时另建列表，是为了避免提前改变历史。两处目的不同。

### 从网址读取当前编号

约定 `/?chat=0` 选择第一段，`/?chat=1` 选择第二段。网页显示可以从“对话 1”开始，内部下标仍从 0 开始。

在 `index()` 开头，用 `request.args.get("chat", "0")` 读取字符串，再用 `int()` 转为整数 `chat_number`。`request.args` 读取网址参数，`request.form` 读取表单输入。

转换放进 `try/except ValueError` 中。转换失败或编号不满足 `0 <= chat_number < len(conversations)` 时，调用 `abort(404)` 拒绝访问；记得在 Flask 导入中增加 `abort`。先验证，再取列表。Python 接受负数下标，但我们的编号约定不接受。

验证后，将固定取第一段的语句改为按 `chat_number` 取出 `history`。请求只能使用这段历史，不能合并整个 `conversations`。

### 增加新建按钮

在 `index()` 后、路由注册前定义 `new_chat()`。它不接收参数，也不调用模型，只做三件事：追加新的空列表，取得其下标，再跳转到对应地址。

用 `append()` 添加新的 `[]`，末项下标是 `len(conversations) - 1`。每次都建立新列表，不能复用旧列表。编号拼进地址前用 `str()` 转为字符串；跳转仍使用 `redirect(..., code=303)`。

保留首页路由，在它附近注册新地址：

```python
app.add_url_rule("/new", view_func=new_chat, methods=["POST"])
```

在 `make_page()` 中增加独立表单，放在发送表单之外，不要嵌套：

```html
<form action="/new" method="post">
  <button type="submit">新建对话</button>
</form>
```

这是 HTML。仿照骨架，把每行作为带引号的字符串追加进 `page`，不要将标签直接当作 Python 语句粘贴。点击后会 POST 到 `/new`，执行新建并跳转。

### 在页面与请求之间保留编号

页面需要知道当前编号。在已有三个参数前加上 `chat_number`，得到 `make_page(chat_number, history, error_text, input_text)`；`index()` 中所有调用也在相同位置传入编号。

在标题后循环生成旧会话入口。用 `range(len(conversations))` 得到各个下标，将下标放进链接地址，将下标加一作为显示编号。例如：

```html
<a href="/?chat=1">对话 2</a>
```

用 `str()` 将整数转成字符串后再拼接。这个循环只生成入口；消息区域仍只遍历所选 `history`。

发送与跳转也要保留编号，否则第二段会话可能把问题发回默认的第一段。检查以下位置是否一致：

| 位置 | 应使用的信息 |
| --- | --- |
| `index()` | 读取、验证 `chat_number`，选择该段历史 |
| `make_page()` 及其调用处 | 接收同一个编号和所选历史 |
| 发送表单的 `action` | 带当前编号，例如 `/?chat=1` |
| 保存成功后的 303 跳转 | 回到相同的带编号地址 |

新建表单仍提交到 `/new`，不要跟着改。可以先实现新建，再添加旧会话链接，最后检查发送与跳转地址。

> **试一试**：在对话 1 说“样品代号是 Q73”，再新建对话 2。检查其首次请求不含 Q73；回到对话 1，旧记录仍在且能继续提问。以实际请求内容为准，不只看模型是否碰巧答对。
