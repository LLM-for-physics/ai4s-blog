132 和 197 已部署 Python 接收端、schema v2 根配置及固定 `ForceCommand`。190 上以真实 importer UID 发起的 SSH 调用已验证：缺失学生账号返回明确的 missing 状态，错误服务器号被拒绝，不会回落到其他服务器执行。

190 到两台目标服务器的实际出口地址经路由检查为 **`162.105.151.77`**，接收端公钥的 `from` 限制已使用该地址。`162.105.151.190` 是当前管理连接使用的地址，不能据此推定出口也为 `.190`。

导入用 SSH 私钥由 importer UID 私有持有，不与 Web 的共享套接字组共享读取权限。目标机接收账号通过固定命令和精确 sudo 规则调用 root helper，公钥安装仍受本机服务器号、学号、`stu` 用户名、允许清单和预期 UID 检查约束。

132 和 197 原有 `/etc/sudoers.d/bin` 的权限为 `0644`，导致 `visudo` 检查失败。本次已先保留 root 备份，再仅将权限改为 `0440`；文件内容哈希保持不变，后续检查通过。该权限修复没有扩展文件中的 sudo 授权内容。

## 回滚注意

1. **不能把 v1 服务直接切到 schema v2 数据库。** 优先使用兼容 schema v2 的修复版本，保留现有数据和明确的迁移记录。
2. 若必须联合恢复旧服务与旧数据，应先停止 Web 和 importer。仅关闭学生入口不会暂停已批准的任务；两个进程停下后，再审查当前写入、任务、备份及三台服务器实际公钥状态。
3. 迁移前快照只代表当时的数据。恢复前必须核对并保留升级后的新增写入，不能用旧快照直接覆盖而丢失新的名单变更、公钥、审批或任务记录。
4. 数据库、允许清单与各机中央公钥不是一个跨服务器事务。需对恢复副本中的未完成任务和已成功记录逐项核对目标、generation、动作和指纹，确认不会重新提交旧任务或将旧公钥以新代次装回去，再决定是否启动服务。
5. **应用或静态页面回滚本身不撤销 SSH 公钥。** 保留现有 SSH 发现路径、中央公钥及代次元数据；不得把删除公钥文件、重置 generation 或移除 SSH Match 当作普通应用回滚步骤。明确需要撤销或恢复钥匙时，仍通过新的更高代次操作完成。
6. 回滚静态页面时也需核对页面与当前 API 的兼容性。上述旧静态版本是本次升级前版本，不代表切换后无需重新检查接口。
